# DATA — централізоване сховище даних

Єдине місце для сирих даних і реєстрів компанії. **Усі AI-агенти, включно з Director, працюють із DATA лише в режимі читання. Записує в DATA лише CEO.**

## Хто що пише

| Що | Хто пише | Ролі |
|---|---|---|
| `inbox/` — сирі експорти й матеріали (реклама, замовлення, витрати, скріншоти, документи постачальників) | **лише CEO** | читають |
| Реєстри (`products-index.md`, інші реєстри за потреби) | **лише CEO** (за пропозицією Director) | читають (Director теж лише читає) |
| Пропозиції оновлення реєстрів і даних | Director, у `REPORTS/` | читають |
| Результати аналізу, розрахунки, звіти | у `WORKSPACE/<роль>/`, не в DATA | пишуть у своє |

Роль, якій потрібні дані, яких немає в DATA, пише запит у своєму `WORKSPACE/<роль>/` файлом `T-..._data-request.md`. Director передає його CEO.

## Структура

```
DATA/
├── README.md
├── products-index.md            ← реєстр товарів (пише CEO за пропозицією Director)
└── inbox/                       ← CEO створює підтеки за потреби
    ├── ads/                     ← експорти рекламних кабінетів
    ├── orders/                  ← експорти замовлень/CRM
    ├── costs/                   ← тарифи, комісії, постійні витрати, рахунки
    ├── competitor-ads/          ← скріншоти/експорти спостережень за рекламою конкурентів
    └── suppliers/               ← умови й документи постачальників
```

## Правила файлів

1. Сирі файли **не змінюються й не перезаписуються**. Оновлення = новий файл.
2. Ім'я: `ГГГГ-ММ-ДД_<джерело>_<опис>.<розширення>`. Для експортів додати період і валюту в назву або перший рядок опису (напр. `2026-11-20_meta-ads_2026-11-13..2026-11-19_UAH.csv`).
3. Кожен експорт має **дату вивантаження** і **період**. Без них дані мають мітку `[НЕВІДОМО]` за періодом.
4. Дані старші за 7 днів у звітах позначаються `[ЗАСТАРІЛО]` (за `STANDARDS.md`).
5. Не змінювати експорт «для зручності»: правки роблять у копії у `WORKSPACE/`.

## Персональні та чутливі дані

- **Перед завантаженням** експортів замовлень CEO маскує ПІБ, телефони, адреси та інші персональні ідентифікатори клієнтів (e-mail, акаунти в месенджерах і соцмережах, будь-які дані, що прямо вказують на особу).
- Якщо роль помічає незамасковані персональні дані, вона не копіює їх нікуди й повідомляє Director.
- У DATA **не зберігати**: паролі, токени, API-ключі, банківські й карткові номери, документи, що посвідчують особу.
- Ролі не копіюють персональні дані клієнтів у звіти чи реєстри.

## Реєстри та порядок оновлення DATA

1. **Роль** зберігає результат у власному `WORKSPACE/<роль>/`.
2. **Director** перевіряє результат (`TEMPLATES/acceptance-checklist.md`). Якщо потрібно оновити реєстр чи додати дані, він готує **пропозицію** `REPORTS/ГГГГ-ММ-ДД_data-update-proposal_<тема>.md`: що змінити, у якому файлі `DATA/`, на підставі яких файлів `WORKSPACE/`, мітки й джерела, невідоме як `[НЕВІДОМО]`. Director **не пише в DATA**.
3. **CEO** затверджує пропозицію й сам переносить дані в `DATA/`.
4. **Director** читає оновлений `DATA/` і фіксує в `STATUS.md`, що перенесено.

Значень не вигадувати: невідоме позначається `[НЕВІДОМО]`. Правила товарного реєстру: `products-index.md`.
