# ТЗ: дата зміни сторінки (`lastmod`) у sitemap.xml raznobyt.com

## Навіщо
`lastmod` підказує Google, які сторінки змінилися і їх варто пересканувати першими. Google враховує `lastmod` лише тоді, коли дати стабільно правдиві. Якщо при кожній збірці ставити всім сторінкам сьогоднішню дату, Google почне ігнорувати це поле. Тому дата має змінюватися **лише тоді, коли змінився вміст саме цієї сторінки**.

## Поточний стан `[ФАКТ, 2026-11-20]`
`sitemap.xml`: 656 URL (328 UA + 328 RU), у кожного `<url>` є `<loc>`, 3 × `xhtml:link` (hreflang), `changefreq`, `priority`. `<lastmod>` немає ні в кого.

## Що зробити

### 1. Формат
- Тег `<lastmod>` у кожному `<url>`, одразу після `<loc>`.
- Формат W3C Datetime, повна дата й час із часовим поясом: `2026-11-20T16:30:10+00:00`.
- Дата не може бути в майбутньому.

```xml
<url>
  <loc>https://raznobyt.com/catalog/workwear/tkan-workwear-tr-55/</loc>
  <lastmod>2026-11-20T16:30:10+00:00</lastmod>
  <xhtml:link rel="alternate" hreflang="uk" href="https://raznobyt.com/catalog/workwear/tkan-workwear-tr-55/"/>
  <xhtml:link rel="alternate" hreflang="ru" href="https://raznobyt.com/ru/catalog/workwear/tkan-workwear-tr-55/"/>
  <xhtml:link rel="alternate" hreflang="x-default" href="https://raznobyt.com/catalog/workwear/tkan-workwear-tr-55/"/>
</url>
```
`changefreq` і `priority` Google не використовує; їх можна лишити або прибрати (на SEO не впливає).

### 2. Що вважається зміною сторінки
**Змінює `lastmod`:** title, description, H1; основний текст сторінки; характеристики картки (склад, щільність, ширина, колір, переплетення, опис); фото товару; ціна чи наявність, якщо колись з'являться на сторінці; перелік товарів на сторінці категорії (додано, прибрано, змінено порядок); тексти й FAQ категорій; вміст службових сторінок.

**Не змінює `lastmod`:** нова збірка без змін вмісту; зміна хешів файлів у `/assets/` (JS, CSS); зміни шапки, меню, футера, телефонів у шапці (вони однакові на всіх сторінках і інакше змінили б дату всім 656 одразу); зміни в блоці «Схожі товари», якщо змінився лише він.

UA і RU мають **окремі** дати: правка лише перекладу змінює дату лише RU-адреси.

### 3. Як рахувати (обрати один варіант)

**Варіант A, рекомендований для статичної збірки: хеш вмісту + файл-реєстр**
1. Під час збірки для кожної сторінки з sitemap взяти **значущий вміст**: title, description, H1, основний блок сторінки (`main` або контейнер вмісту), без `<script>`, `<style>`, шапки, меню, футера й блоку «Схожі товари».
2. Нормалізувати (прибрати зайві пробіли) і порахувати хеш (SHA-256).
3. Зберігати реєстр `lastmod-manifest.json` між збірками (у репозиторії або поруч із проєктом; **не** на сайті):
   ```json
   {
     "/catalog/workwear/tkan-workwear-tr-55/": { "hash": "a3f25d…", "lastmod": "2026-11-20T16:30:10+00:00" }
   }
   ```
4. При збірці: якщо хеш сторінки збігся з реєстром, лишити стару `lastmod`; якщо змінився або сторінка нова, `lastmod` = час збірки (UTC), оновити реєстр. Сторінки, яких більше немає, прибрати з реєстру й sitemap.
5. **Перший запуск:** реєстру ще немає, тому всім сторінкам ставиться дата першого запуску. Це нормально, один раз.

**Варіант B, якщо дані товарів беруться з бази чи CRM із полем дати зміни (`updated_at`)**
- Картка: `updated_at` товару (і окремо `updated_at` перекладу для RU, якщо є).
- Категорія: найпізніша з дат: зміна тексту категорії й зміна складу її товарів на першій сторінці.
- Головна, службові сторінки: дата зміни їхнього контенту (дата коміту файлу в git або поле в даних).
- Якщо поля дати для частини сторінок немає, для них використати варіант A.

Звідки сайт бере дані товарів, `[НЕВІДОМО]`; розробник обирає варіант за фактичним кодом і пише в результаті, який обрав.

### 4. Що не робити
- Не ставити всім сторінкам дату поточної збірки.
- Не брати дату з `Last-Modified` файлу на сервері: при кожному завантаженні сайту вона стає новою для всіх файлів `[ФАКТ: 20.11 у всіх 656 сторінок Last-Modified = дата завантаження]`.
- Не змінювати `<loc>`, hreflang, canonical: вони зараз правильні.

## Критерії приймання
1. У `sitemap.xml` кожен з 656 (або актуальної кількості) `<url>` має рівно один `<lastmod>` у форматі `YYYY-MM-DDThh:mm:ss+00:00`; XML коректний (відкривається в браузері без помилок).
2. Жодна дата не в майбутньому.
3. **Тест «без змін»:** дві збірки поспіль без змін вмісту дають однакові `lastmod` у всіх URL.
4. **Тест «одна правка»:** змінити опис однієї картки лише в UA, перезібрати: змінилась `lastmod` лише цієї UA-картки (і, якщо зміна впливає на перелік товарів, сторінки її категорії); RU-версія й інші сторінки без змін.
5. **Тест «шапка»:** змінити текст у футері, перезібрати: жодна `lastmod` не змінилась.
6. `lastmod-manifest.json` не доступний за адресою на сайті (`https://raznobyt.com/lastmod-manifest.json` → 404).
7. hreflang (3 на URL), кількість URL і `<loc>` такі самі, як до змін.

## Після впровадження
CEO повторно подає `sitemap.xml` у Google Search Console («Файли Sitemap»). SEO Specialist перевіряє критерії 1, 2, 6, 7 на живому сайті; критерії 3–5 перевіряє розробник на своїй копії й описує в результаті.
